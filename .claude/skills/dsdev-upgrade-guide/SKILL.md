# 升级指南

升级指南告诉运行版本 vT 的读者要改什么才能运行下一个版本。**在引入破坏的变更里、认识到破坏的那一刻写**，不要推到发版准备。

## 范围

只为仓库外的人升级后能观察到的破坏写：

- CLI 命令、标志、profile/模式名；
- 配置文件、patch/overlay、设置键或它们接受的值；
- 持久化的用户数据：日志、数据库、用户数据目录；
- SDK 导出、RPC/HTTP/协议消息；
- 发布的包名与入口。

预稳定的内部 API 在同一变更里更新了所有消费者时不需要指南。持久化格式变更仍要走项目的类型变更确认流程；它的指南只写读者的动作并链接那条记录。

## 位置

`docs/upgrade-guide/v<version>/<item>/guide.md`

- `<version>` 是写指南时根 `package.json`（或等价）的 `version`，例如 `v0.1.7-rc.2`：指南描述从该发布到下一个发布的升级。
- `<item>` 是被改面的 kebab-case 名，例如 `profile-flag-rename`。
- 每个 item 目录只放 `guide.md`（及项目要求的译文与配对记录）：没有索引，没有附件。

## 内容

```markdown
---
kind: upgrade-guide
description: "破坏的外部面与替代物。"
---

# <具体的破坏，例如：`--profile` 替代 `--preset`>

## Change

陈述该面的旧行为与新行为，以及谁会观察到。

## Migration

1. 命名要改的精确文件、键、命令或符号，前后片段比散文短时给片段。
2. 说明如何确认迁移成功。
```

## 维护

- 同一发布周期内再次改动同一面 → 更新已有指南，不新建。
- 面被进一步破坏到指南不再准确 → 重写该指南以描述从 vT 到下一发布的净变化。
- 发布后指南冻结；下一发布周期的破坏写到新的 `v<next>/` 目录。
- `verify-upgrade-guides` 检查目录布局、frontmatter、必需章节与长度上限（600 词，CJK 字符各算一词；DS 原版是 500 英文词）。超了就把背景搬去文档或 Agent Note，只留读者的动作。

## 报告

报告：被破坏的面、指南路径、是新建还是更新、实际运行的检查。
