# 文档与散文标准

写到足以保留契约，然后删掉推理记录、重复和装饰。**契约**是调用者、被调用者、实现者、生产者或消费者依赖的义务、不变量、前置/后置条件、兼容性承诺。这是指导不是脚本。细则见 [references/](references/)。

## 一事一家：层级与放置

每个事实只有一个家，别处放链接。

| 层 | 职责 | 不属于这里 |
|---|---|---|
| 根 `AGENTS.md` | 常备命令：Agent 每次会话都需要的规则，每条 1–3 行并链接其家 | 故事、示例、情境流程、从链接目标复述的内容 |
| 子树 `AGENTS.md` | 该子树特有的命令 | 根文件已有的全仓库规则 |
| `docs/architecture.md` | 有序地图：组合、核心模块、主循环、扩展点；改核心前必读 | 类型定义、单模块细节、决策理由、实现状态标注 |
| `docs/subsystems/`（或等价） | 每子系统一页参考：类型定义、语义、生成的 API | 行为叙述 |
| Agent Notes | 活跃决策记录：why、放弃了什么、需要的验证 | 上线后的迁移计划、验收清单、"should…" 口吻 |
| `docs/defensive-patterns/` | review 执行的规则，按工件分页 | 类型定义、决策理由 |
| `docs/postmortem/` | 事故故事——唯一允许叙事的层 | — |
| `docs/cookbook/` | 带编号验证步骤的 how-to | 设计理由 |
| 模块 README | 模块契约：配置、语义、限制、扩展点、模型可见效应 | JSDoc 复述、生成目录复述、别的模块的事 |
| `docs/development.md` | 贡献者环境、日常流程、CI 概要 | 版本理由、会与脚本漂移的逐项清单 |
| 生成的参考 | 由源码再生并做新鲜度 gate | 手改 |
| skills | 可复用工作流与决策标准 | 产品与运行时契约 |

放置口诀：bug → postmortem；理由 → Agent Note；流程 → cookbook；类型 → subsystems；模块契约 → README；常备命令 → 根 AGENTS.md 加理由链接；review 执行的规则 → defensive-patterns。

把每篇面向人的文档分类为**教程**（有序路径到结果，每步只引入所需）或**参考**（定义查找范围与当前行为，无教学顺序）；实质混合的要分开。写教程前私下把读者起点与每个概念分成初/中/高级，先建前置再讲依赖。

## 写作规则

- **写当前状态。** 历史留在提交、PR、Agent Note、postmortem。散文命名活着的机制，不命名变更或 stack 位置。
- **一个段落一个物理行**（`verify-md-wrap`），用编辑器软换行；代码块、表格、列表保留格式。
- **带 `ts` 标记的代码块必须编译**（有 doc-typecheck 的项目）；粘贴的类型声明用等价标记并登记到清单，防止漂移。
- **改了被文档化的类型就同一变更更新拥有它的子系统页。**
- **一个仓库一种文档语言**：README、docs、Agent Note、postmortem、注释的正文用同一种语言；机器检查的结构 token（`# Agent Note:`、`Status:`、`## Problem`/`## Decision`、PR 模板的 `## Motivation` 等）保持英文原样，不算混语。写新文档前看一眼同类文件用的是哪种语言。维护双语的仓库按配对规则两边一起改并重新记录，任何一边都可以是本次的权威。
- **注释与 JSDoc 陈述完整契约，不是推理记录。** 保留行为、失败、时机、所有权、模态、例外、后果、非显然的定位；删除叙述、测试走读、评审分析、代码复述。
- **直接写：命名行为者与事实。** 不用隐喻。写 `contract`/`boundary`/`shape`/`surface`/`seam`/`gate`/`vocabulary` 之前先问有没有更精确的词（`response fields`、`JSON validation`、`ESM exports`）；`contract` 留给真正的义务，`boundary` 留给字面的进程/线上/安全/事务/生命周期边界。
- **历史引用用 tag、Issue 或 PR 号，不用提交哈希**（`verify-repository-references`）；必须引用提交时在该行标 `<!-- commit-ref-ok -->` 并说明原因。
- **文件以恰好一个换行结尾**；`git diff --cached --check` 守门。

## 字数预算

常备文档的上限在 `scripts/doc-budgets.manifest.json`，`verify-doc-budgets` 执行。变红时按顺序：**搬迁**属于别层的内容（留一行链接）→ **压缩**属于这里但能更短的 → **提高上限**仅当内容确实需要空间，并在 PR 里说明。上限是护栏不是削减目标：在目标以下保留 ≥5% 余量；以上时冻结上限直到搬迁/压缩回到目标以下。

## 各类散文的必需覆盖

这不是单向的缩短。代码、类型、结构表达不了下列契约时要补或恢复散文；已经本地显然时不要加。

- **公开 JSDoc**：调用者可见的返回区别、throw/reject、副作用、所有权、时机、取消、持久性；函数式导出带 `@param`/`@returns`。
- **内部注释**：定位非局部结构与显然复杂的局部结构：不变量、竞态顺序、所有权、安全边界、意外失败行为。删控制流叙述与代码复述。
- **模块注释**：模块角色、依赖、职责、非显然的架构选择并链接其解释。
- **测试**：只解释非显然的设计：为什么需要某 fixture、断言、平台适配、真实入口路径、间接观察。删走读与清单。
- **cookbook**：前置条件、必需动作、真实入口路径、可观察的验证、简洁警告。
- **README**：消费者契约：配置、语义、失败、限制、扩展点、模型可见效应；引用模块拥有的稳定模型可见文本；链接生成目录与跨模块所有者。保留持久缺口与维护者陷阱，不保留普通清理清单。
- **Agent Note**：独有的理由、机制、备选、后果、上线的验证证据、命名的覆盖缺口。implemented 用现在时。
- **postmortem**：事故序列、证据、因果链、影响、预防。删重复说服与不建立因果的实现细节。
- **skill 与 agent 指令**：行为护栏与明确的范围限制（"指导不是脚本"）。工作流简洁，链接真相来源。
- **示例与配置注释**：访问限制、非显然接线/加载顺序、安全立场、回放行为、例外、可能误用。不叙述配置已经显示的条目。
- **提示词与可见字符串**：措辞即行为。模型可见文本的变更更新拥有它的快照；授权范围内没有拥有场景时保持原文并报告推迟，不要悄悄并入纯散文改动。
- **诊断**：命名失败的对象/路径、违反的规则、非显然时的修正。删内部执行叙述。

保留可搜索的机制名与有意义的模态/时间/否定强调；只规范装饰性强调。

## 保留完整命题

编辑前列出段落里的每个命题，保留每个相关的：行为者与动作；条件、时机、顺序；模态（must/may/never）；负向保证与例外；所有权、副作用、失败模式、后果。只在每个事实子句都存活且结果更清晰时删形容词、重复、叙述。更少的字数本身不是改进。

在使用点保留完整的局部契约（行为、失败、所有权、后果），对架构、理由、算法、历史、扩展示例激进地链接到拥有文档。

## 思维链泄漏："一个测试"

对每段可疑文字问：**HEAD 处的读者，不看任何会话记录、PR 线程、未提交草稿，能解析每个引用、核实每个声明吗？** 不能 → 从仓库视角重述幸存的事实，删掉其余。能 → 不是泄漏，但在当前状态面（README、docs、JSDoc）上可解析的变更故事仍是变更叙述，路由到它许可的家。

八类泄漏：死的设计会话引用（`(decision 7)`、`§4.7`、阶段标签）；stack/PR 视角（"a later PR in this stack"）；变更叙述与版本戳（"used to"、"no longer"、"this cut"）；评审编排（"Rejected in review:"）；对评审者的辩护（"this is safe because…"→陈述使代码安全的不变量，或代码已显示就删）；复述与推导记录（控制流叙述、测试走读）；含糊与计划残留（"probably fine for now"→提升为 TODO/FIXME 或写实际界限）；工作语言混入。

不是泄漏（不要误删）：Issue 引用；Agent Note/postmortem 内对已合并 PR 的引用；lint 抑制理由与空 catch 说明；现在时反事实回归钉（"without X, Y happens"）；标注了 `measured` 的测量界限；运行时的 old/new 状态；外部标准的 § 编号；项目之声的"we"。

## 事实核查：测试，不要假设

文档陈述产品今天的行为，操作性声明唯一可接受的证据是**跑过它**。对每篇新文档和每段声称操作/命令/默认/错误/平台差异的新段落：先按事实（manifest、入口文件）分类对象；对当前 checkout 逐条执行文档将展示的命令/配置并只写观察到的；无法复现的删除——修声明不修测试；改旧文档前对比最新主干；双语配对每次编辑后重新记录。

## slop 清单（审计用）

重复规则（搜一个独特短语，留一个家）；越层的历史；实现状态标注（"implemented!"、"future:"）；手抄的目录/JSDoc/测试清单；推理记录；在兄弟方法旁重复的理由；段落墙；强调通胀；implemented note 里的 spec 口吻。

## 工作流

1. 确认范围、模式（automatic|interactive，默认 automatic；模式控制提问不控制写权限：review/audit 只报告，明确的 write/fix/trim 才改）、当前分支或 PR base、适用的 `AGENTS.md`。排除 vendor 与归档 note。
2. 判断一段文字之前先读文档标准与拥有的代码或文档。
3. 检查请求的范围而不只是最大的文件；用搜索和字数找候选，然后语义判断。
4. 每个候选分类：keep / add / trim / restore / restructure / defer。不为满足删减目标制造编辑。
5. 先改所有者再改派生物（生成目录、快照、双语对）。学到新规则后复查类似段落。
6. 跑窄的相关检查、文档 gate、`git diff --check`、可见字符串的行为测试。
7. 报告检查的范围、明确的改动、有意保留、推迟的案例、实际运行的检查。

边界案例（两个版本都满足完整命题但权衡被接受的原则）在 automatic 模式报告不提问；interactive 模式按原则分组给 2–3 个可行版本并推荐一个。用户决定后把原则与版本提炼到 [references/examples.md](references/examples.md) 并应用到范围内所有类似段落。
